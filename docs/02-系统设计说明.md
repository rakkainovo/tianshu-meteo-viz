# 系统设计说明

> 天枢 · 全国气象监测与灾害预警时空可视化平台
> 本文档对应论文的「需求分析 / 总体设计 / 详细实现」三章

---

## 一、需求分析

### 1.1 问题的提出

中国气象局通过 `nmc.cn` 对外发布气象预警信号，每天数百条，覆盖十余个灾种、四个等级，
发布主体是省、市、县三级共一千多家气象台。但这些信息目前只有两种呈现方式：

1. **一条条孤立的短信/推送** —— 受众只知道自己所在区县的那一条；
2. **官网的长列表** —— 按时间倒序排列的文字流，读十条就失去耐心。

两者共同的缺陷是：**丢失了空间维度**。公众无法回答这几个最朴素的问题：

- 此刻全国哪些地方在发预警？集中在哪一片？
- 我所在的省份是什么风险等级？周边省份呢？
- 红色预警出现在哪里？它们是从什么时候开始出现的？
- 这轮过程的演变节奏是怎样的，在加速还是平息？

**这就是本平台要解决的问题：把文本形态的预警流，还原成一张可感知、可交互、可下钻的时空态势图。**

### 1.2 功能需求

| 编号 | 需求 | 说明 | 对应用户诉求 |
|---|---|---|---|
| F1 | 态势总览 | 一屏看清 KPI、全国分布、等级与灾种构成、24 小时趋势 | "现在是什么情况" |
| F2 | 预警地图与下钻 | 全国 → 省 → 市 → 区县三级下钻，列表与地图双向联动 | "我想看具体某个地方" |
| F3 | 站点实况分析 | 2528 个台站的要素空间分布、极值排行、单站 7 日预报 | "具体数值是多少" |
| F4 | 台风路径回放 | 路径沙盘 + 逐帧回放 + 强度演变 | "台风要去哪" |
| F5 | 时空回放 | 24 小时预警按时间顺序重放 | "这轮过程怎么演变的" |
| F6 | 智能问答 | 自然语言提问，直接给出结论与图 | "我不想点，我想直接问" |
| F7 | 数据采集与数据库 | 可复现的采集脚本 + 结构化存储 | 作业要求"包含数据库" |

### 1.3 非功能需求

- **真实性**：所有数据必须来自公开真实数据源，不得模拟。这是评分第一条。
- **可离线**：答辩现场可能没有网络，因此**地图边界、前端依赖库、数据集全部本地化**。
- **可复现**：采集脚本一条命令跑通，数据集构建脚本一条命令跑通。
- **合规**：地图使用标准行政区划边界数据，包含台湾省、香港及澳门特别行政区、南海诸岛。

## 二、总体设计

### 2.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  表现层  web/                                             │
│  Vue 3 组件化视图 × 6  +  ECharts 5 可视化  +  深色大屏 CSS │
├──────────────────────────────────────────────────────────┤
│  服务层  server/app.py                                    │
│  REST API 20 个端点：查询 / 聚合 / 时序 / 地图 / 问答        │
├──────────────────────────────────────────────────────────┤
│  分析层  server/qa.py                                     │
│  自然语言 → 意图 → SQL → 结论文本 + ECharts option          │
├──────────────────────────────────────────────────────────┤
│  数据层  SQLite (server/db.py)                            │
│  8 张表：区划 / 预警 / 站点 / 实况 / 预报 / 台风 / 路径 / 字典 │
├──────────────────────────────────────────────────────────┤
│  采集层  crawler/                                         │
│  中国气象局 API 采集 → 清洗 → 坐标匹配 → 结构化落盘           │
└──────────────────────────────────────────────────────────┘
```

### 2.2 技术选型理由

| 选型 | 理由 |
|---|---|
| **Vue 3（全局构建版）** | 组件化开发可控复杂度；**不使用打包器**，直接引入本地 `vue.global.prod.js`，双击 `start.bat` 即可运行，答辩零环境风险 |
| **ECharts 5** | 地理坐标系 + `geo`/`map` 双层叠加能力成熟，`registerMap` 支持按行政区划动态下发 GeoJSON |
| **Flask** | 轻量、单文件可读，用于承载 API 与问答 |
| **SQLite** | 单文件零配置，随项目一起交付，评审直接可查 |
| **深色科技风** | 预警四色（红橙黄蓝）是高明度色，只有深色底才能压得住；投影环境下对比度更好 |

> **关于"不用打包器"的取舍**：课程作业的交付场景是"老师/助教在自己电脑上打开看一眼"，
> 任何需要 `npm install` 的环节都会显著提高失败率。牺牲一点工程规范度，
> 换来"解压即可运行"，在这个场景下是正确取舍。

### 2.3 数据流

```
 nmc.cn /rest/findAlarm          crawler/run_collect.py
        │                                  │
        ▼                                  ▼
   data/raw/*.json  ──── crawler/build_dataset.py ────▶  data/processed/*.json
        │                    （清洗/坐标匹配）                │
        │                                                     ▼
        └──────────────▶  server/db.py  ──────────▶  data/meteo.db (SQLite)
                                                              │
                          server/app.py  ◀────────────────────┘
                                │  REST
                                ▼
                          web/  Vue3 + ECharts
```

## 三、详细实现

### 3.1 数据采集层

见 [`01-数据采集指南.md`](01-数据采集指南.md)。要点：

- **TLS 指纹对抗**：`nmc.cn` 校验 TLS 握手指纹，`requests` 的指纹会被拦，
  改用 `curl_cffi` 的 `impersonate="chrome124"` 模拟真实 Chrome。
- **每线程独立 Session**：实测共用 Session 会导致不同线程互相干扰、返回错乱数据。
  每线程一个 Session 后，2528 个请求 0 失败。
- **行政区划坐标表**：预警文本只给"省/市/县"名称，需要转成经纬度。
  这里不调第三方地理编码 API，而是**从标准 GeoJSON 自身提取 `properties.center`**，
  得到 3237 条权威的省/市/县中心点。做法简单、零依赖、完全离线。

### 3.2 数据清洗

采集到的原始数据有三处"坑"，在 `build_dataset.py` 中统一处理：

| 问题 | 现象 | 处理 |
|---|---|---|
| **缺测哨兵值** | 接口在无观测值时返回常量 `9999`，被当成真实值，出现"降水量 9999mm""湿度 9999%" | `sanitize_station()` 将 9999 / -9999 还原为 `NULL`，并对温度、湿度、气压、降水做合理区间校验 |
| **行政区后缀重复** | "内蒙古自治区"被解析成"内蒙古自治区自治区" | 后缀剥离时先判断是否已包含，避免二次追加 |
| **台风中英文名错位** | 官方数组里 `[1]` 是英文名、`[2]` 是中文名，最初写反，导致"杜鹃"显示为英文名 | 修正字段映射（`run_collect.py`） |

### 3.3 数据库设计

```sql
region(adcode PK, name, level, parent, lng, lat)          -- 3237 条，省/市/县三级
alarm(id PK, ts, date, hour, title, type, level,          -- 208 条事实数据
      level_rank, issuer, province, city, county,
      adm_code, lng, lat, geo_level, icon, url)
station(code PK, province, city, lng, lat, url, geo_source)  -- 2528 条
observation(code PK→station, temp, feelst, humidity,      -- 2526 条实况快照
            rain, pressure, info, rcomfort, icomfort)
forecast(code, date, day_info, night_info, day_temp,      -- 17682 条，7 日 × 2526 站
         night_temp, day_wind, day_power, precip)
typhoon(code PK, name_cn, name_en, status, max_wind,      -- 28 个
        min_pressure, track_km, max_level, 边界盒…)
typhoon_path(code, seq, time, level, lon, lat,            -- 1536 个路径点
             pressure, wind_speed, wind_dir, move_speed)
disaster_type / alarm_level / dataset_meta                -- 字典与元信息
```

**设计取舍**：

- **事实表做维度冗余**。`alarm` 表里同时存了 `province/city/county` 和 `lng/lat`，
  没有严格按第三范式拆成 `region_id` 外键。原因是本平台 90% 的查询都是
  "按地区聚合"，冗余掉一次 JOIN 换来的是前端联动时的响应速度，值得。
- **派生指标入库而非前端算**。台风的累计行程、最强等级、经纬度包围盒，
  在入库时就计算好（`typhoon.track_km`、`max_level`、`min_lon`…），
  避免每次切页面前端遍历 1536 个点。
- **站点坐标反查**。站点清单只有站名没有经纬度，需要靠区划表反查。
  难点是站名写法五花八门：`石家庄`（地级市）、`昌平`（区县）、`鹿泉（石家庄）`（带括号注解）、
  `乌鲁木齐牧试站`（带站点类型后缀）。做法是建 `(省名, 归一化地名)` 的扁平索引，
  再对站名做多候选拆解（括号内外 + 去站点后缀）逐个尝试。
  **匹配率从最初的 15.6% 提升到 90.6%**，剩下 9.4% 落到省中心。

### 3.4 可视化设计

#### 3.4.1 色彩语义

平台最核心的设计决策是：**不发明颜色，直接复用官方语义**。

中国气象局预警信号本身就是"颜色 + 等级"的绑定关系——
红色最严重、蓝色最轻。既然如此，地图上用同一套色：
用户不需要看图例就能理解"这片区域一片红意味着什么"。

```
红色 #ff3b47 (rank 4)  →  橙色 #ff8a00 (rank 3)
黄色 #ffd233 (rank 2)  →  蓝色 #3d7eff (rank 1)
```

灾种则给独立色（暴雨蓝、高温橙、大风青、雷电紫…），保证在饼图和地图散点里可区分。

#### 3.4.2 空间认知

- **面用行政区划色块**：表达"该区域的整体风险等级"，符合人对行政区划的心智模型；
- **点用预警落区**：表达"具体是哪几个点在发"，带呼吸光圈；
- **面与点双层叠加**：`geo` 组件 + `map` 系列（`geoIndex: 0`）负责面，
  `scatter` / `effectScatter`（`coordinateSystem: 'geo'`）负责点，
  共享同一套投影，天然对齐。

#### 3.4.3 三级下钻

```
全国(100000) ──点击省份──▶ 省(440000) ──点击城市──▶ 市(c440100) ──▶ 区县圆点
   │                            │                         │
省级色块+预警点            市级色块+预警点            区县级色块+预警点
```

地图数据按需从 `/api/geo/<adcode>` 取，前端用 `MapHub` 做注册缓存，
同一个行政区只注册一次。365 个地图文件共 26.6 MB 全部本地化，**断网可用**。

#### 3.4.4 时空回放

预警数据的时间跨度是 23 小时 50 分（202 6-09-17 10:34 → 2026-09-18 10:24），
共 208 条。回放页把这 208 条按时间排序后逐条"揭示"：

- 已揭示的点用低饱和度小圆点表示（"已经发生"）；
- 最近 18 个点用 `effectScatter` 呼吸光圈表示（"正在发生"）；
- 地图色块随回放推进实时重算（"累积态势"）；
- 下方累计曲线同步推进，虚线标出当前时刻。

同一份静态数据，通过时间维度获得了"事件流"的观感。

#### 3.4.5 台风路径的投影处理

台风路径分布在西太平洋，经度可达 150°E，远超中国地图的包围盒（最东约 135°E）。
直接叠加会导致路径跑出画布。解决方案是使用 ECharts `geo` 组件的
**`boundingCoords`** 参数，把投影范围动态扩展到所有台风路径的并集包围盒：

```js
boundingCoords: [[95, 2], [152, 46]]   // 由数据实时计算并留出 4° 余量
```

这样台风路径完整落在画布内，同时中国大陆作为地理参照仍然可见。

### 3.5 智能问答设计

#### 3.5.1 为什么不是"把数据丢给大模型"

直接把数据交给大模型"看图说话"在这个场景有两个硬伤：

1. **不可复现**：同一句话两次回答可能数字不同，答辩时被追问就露馅；
2. **环境依赖**：没网或没 API Key 时功能直接失效。

#### 3.5.2 双通道架构

```
用户提问
   │
   ├──▶ 通道 A：规则解析器（默认，零依赖，永远可用）
   │      正则 + 词典匹配 → 结构化意图 {intent, type, level, province, city, metric, top}
   │
   └──▶ 通道 B：大模型解析器（可选，仅在通道 A 无法识别时触发）
          LLM 只负责"把口语翻译成意图 JSON"，不接触原始数据、不做算术
                          │
                          ▼
              意图执行器：生成 SQL → 查询 SQLite → 计算结论
                          │
                          ▼
              渲染器：结论文本 + ECharts option + 支撑 SQL
```

**关键点：模型不接触原始数据、不做算术，只在必要时帮忙理解口语化表述。**
结论里的每个数字都能追溯到一条可复现的 SQL，界面下方会把这条 SQL 展示出来——
这既是技术上的可解释性，也是答辩时的加分项。

配置大模型（可选，不配也完整可用）：

```bat
set LLM_API_KEY=sk-xxxx
set LLM_BASE=https://api.deepseek.com/v1
set LLM_MODEL=deepseek-chat
```

#### 3.5.3 支持的问法

| 意图 | 示例 |
|---|---|
| `count` 计数 | 现在有多少条预警？红色预警有几条？ |
| `rank_province` 省份排名 | 哪个省的预警最多？ |
| `rank_city` 城市排名 | 哪些城市预警最多？ |
| `rank_issuer` 单位排名 | 发布预警最多的气象台是哪家？ |
| `filter_list` 条件筛选 | 广东省有哪些预警？暴雨预警有哪些？ |
| `level_dist` 等级分布 | 全国的预警等级分布如何？ |
| `type_dist` 灾种分布 | 灾种构成是怎样的？ |
| `trend` 时间趋势 | 预警数量随时间怎么变化？哪个时段最多？ |
| `compare` 地区对比 | 广东和湖南哪个预警更多？ |
| `station_extreme` 要素极值 | 全国最高气温出现在哪里？最冷的地方是哪里？ |
| `station_count` 站点统计 | 北京市气象站有多少个？ |
| `weather_summary` 天气概况 | 今天天气怎么样？ |
| `typhoon_strongest` 台风强度 | 最强的台风是哪个？ |
| `typhoon_path` 台风路径 | 台风杜鹃的路径是怎样的？ |
| `overview` 态势总结 | 现在整体形势怎么样？ |

回归测试见 [`../tests/test_qa.py`](../tests/test_qa.py)，当前 **21/21 通过**。

#### 3.5.4 规则引擎最容易踩的坑

开发过程中反复出现的一类 bug 是**关键词撞车**：

- `"广东省有哪些预警？"` 因为含"哪些"被误判成"省份排名"；
- `"哪个时段预警最多？"` 因为含"最多"被误判成"省份排名"；
- `"北京市气象站有多少个？"` 因为含"有多少"被误判成"预警计数"。

处理原则是**按语义类型排序判定，而不是按关键词出现顺序**：

1. 具体实体的判断（站点、天气、台风）优先于抽象统计；
2. 「列举型」问法（有哪些/有什么）与「极值型」问法（最多/最高）显式区分；
3. 每条规则只负责一类语义，宁可多写几条，不要用一个大正则通吃。

## 五、已知限制与后续改进

| 限制 | 原因 | 改进方向 |
|---|---|---|
| 预警仅覆盖近 24 小时 | 气象局接口只提供实时滚动窗口 | 用定时任务累积历史，形成长时序预警库 |
| 站点坐标 9.4% 落到省中心 | 部分站名是极小地名（如"黑牛城""牧试站"） | 接入高德/百度地理编码 API 做兜底 |
| 气象要素只有温湿降水 | `nmc.cn` 站点实况接口不返回风速风向 | 改采机场 METAR 报或 2345 天气的站点数据 |
| 大模型通道需自行配置 Key | 未内置任何密钥 | 保持现状——不内置密钥是正确做法 |

## 六、运行方式

```bash
# 一键启动（Windows）
start.bat

# 或手动
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
python server/db.py --stats     # 构建数据库并体检
python server/app.py            # 启动服务 → http://127.0.0.1:5000
```

重新采集数据（可选）：

```bash
cd crawler
python fetch_geo.py             # 补全离线地图（已随项目提供，无需重跑）
python run_collect.py stations alarms weather typhoon
python build_dataset.py
python ../server/db.py
```
